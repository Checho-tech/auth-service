        GET    /api/v1/users              (requiere users:read)
        PATCH  /api/v1/users/{id}/roles   (requiere roles:manage)
        DELETE /api/v1/users/{id}         (requiere users:delete)
        GET    /api/v1/audit-logs         (requiere audit:read)

  [x] Decision de diseno clave: los permisos se verifican consultando la
      base de datos EN CADA REQUEST (no se confia en lo que dice el JWT),
      asi que si un Admin le quita un permiso a un rol, aplica en la
      siguiente peticion inmediatamente, no cuando expire el token de
      15 minutos. Verificado en vivo: se promovio un usuario a admin via
      API y, CON EL MISMO access token emitido antes de la promocion
      (sin volver a hacer login), ya pudo acceder a /audit-logs.

  [x] BUG DE SEGURIDAD REAL encontrado y corregido durante las pruebas:
      un usuario desactivado (DELETE /users/{id}) SI podia volver a
      hacer login y obtener tokens nuevos, anulando la desactivacion.
      Se agrego la verificacion "is_active" en AuthService.login()
      (dominio: nueva excepcion AccountDeactivatedError). Verificado:
      ahora el login de una cuenta desactivada devuelve 403.

  [x] Verificacion funcional completa contra Postgres real (mismo patron
      de las fases anteriores, contenedor temporal ya eliminado): se

      sesion de tests, corre las migraciones, y se autodestruye al final).
      No se agrego ninguna libreria nueva para esto (no testcontainers):
      se reutilizo subprocess + docker CLI, exactamente el mismo script
      que ya habiamos validado que funciona en este Mac.

  [x] PROBLEMAS TECNICOS ENCONTRADOS Y RESUELTOS (no eran bugs de la app,
      sino de como correr los tests):
        1. pytest-asyncio crea un event loop nuevo por cada test por
           defecto, pero el motor de base de datos de la app es un
           singleton a nivel de modulo (igual que en produccion, donde
           solo hay un event loop para toda la vida de la app). Esto
           causaba errores "attached to a different loop". Solucion:
           configurar pytest-asyncio para compartir un unico event loop
           en toda la sesion (asyncio_default_test_loop_scope = "session"
           en pyproject.toml).
        2. El rate limit de login (5/minuto) se disparaba entre tests
           porque todos comparten la misma "IP" simulada del cliente de
           pruebas. Solucion: se sube ese limite SOLO en el entorno de
           tests (variable de entorno RATE_LIMIT_LOGIN), sin tocar el
           limite real de produccion.

  [x] Se aprovecho para pasar "ruff" (el linter) sobre todo el codigo y
      corregir 90+ advertencias de estilo (lineas largas, una variable
      sin usar). Cero advertencias ahora: "ruff check src tests" -> OK.

  [x] Resultado final: 30/30 tests pasan (pytest -q). El contenedor de
      Postgres de test se crea y se destruye solo en cada corrida, no

[2026-07-28] RETROFIT: HS256 -> RS256 + ENDPOINT JWKS
--------------------------------------------------------------------

  Motivo: empezamos el proyecto 2 (Inventory Service), que necesita
  verificar los JWT de este servicio sin autenticar nada localmente.
  Con HS256 (secreto compartido) habria que copiar el mismo
  JWT_SECRET_KEY en cada microservicio nuevo -- riesgo de seguridad
  que crece con cada servicio agregado. RS256 lo resuelve: la clave
  privada nunca sale de aqui, la publica se reparte sin riesgo.

  [x] Generado par de claves RSA 2048-bit con openssl:
        keys/private.pem  (NUNCA se sube a git, ya en .gitignore)
        keys/public.pem   (tampoco se sube; cada quien genera el suyo)

  [x] config.py: reemplazado "jwt_secret_key" por "jwt_algorithm=RS256",
      "jwt_private_key_path", "jwt_public_key_path", y una propiedad
      "jwt_key_id" (fingerprint de la clave publica, usado como "kid"
      en el header del JWT para soportar rotacion de claves a futuro).

  [x] jwt_handler.py: firma con la clave privada, verifica con la
      publica (antes ambas operaciones usaban el mismo secreto).

  [x] Nuevo endpoint: GET /.well-known/jwks.json (formato estandar
      JWKS, RFC 7517) -- publica la clave publica para que cualquier
      servicio la consuma. No se agrego ninguna dependencia nueva
      (la libreria "cryptography" ya venia con pyjwt[crypto]).

  [x] Tests: se genera un par de claves RSA DESECHABLE en memoria para
      cada corrida de tests (nunca un PEM fijo commiteado, eso lo
      marcaria un secret-scanner de Github). Extraido a un helper
      compartido: tests/rsa_test_keys.py (evita duplicar codigo entre
      tests/unit/conftest.py y tests/integration/conftest.py).

  [x] docker-compose.yml: la carpeta keys/ se monta como volumen de
      solo lectura en el servicio "app" (nunca se hornea en la imagen
      Docker -- ver .dockerignore). Rotar la clave = reemplazar el
      archivo en el host, no reconstruir la imagen.

  [x] Verificado en vivo con docker compose: JWKS responde correctamente,
      el flujo completo de auth sigue funcionando, y se probo que un
      CLIENTE EXTERNO (usando PyJWT's PyJWKClient, exactamente como lo
      hara Inventory Service) puede verificar un token consultando SOLO
      el endpoint JWKS, sin conocer jamas la clave privada.

      variables de entorno, instrucciones de instalacion).
