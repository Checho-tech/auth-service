[2026-07-27] FASE 4 - AUTORIZACION (ROLES Y PERMISOS)
--------------------------------------------------------------------

  [x] Implementado: dependencia "require_permission(codigo)" reutilizable
      en cualquier endpoint, servicio UserManagementService (listar
      usuarios, asignar roles, desactivar usuario, leer audit log), y
      4 endpoints nuevos protegidos por permiso especifico:
        GET    /api/v1/users              (requiere users:read)
        PATCH  /api/v1/users/{id}/roles   (requiere roles:manage)
        DELETE /api/v1/users/{id}         (requiere users:delete)
        GET    /api/v1/audit-logs         (requiere audit:read)

  [x] Decision de diseno clave: los permisos se verifican consultando la
      base de datos EN CADA REQUEST (no se confia en lo que dice el JWT),
      asi que si un Admin le quita un permiso a un rol, aplica en la
      siguiente peticion inmediatamente, no cuando expire el token de
      15 minutos. Verificado en vivo: se promovio un usuario a admin via
      API y, CON EL MISMO access token emitido antes de la promocion
      (sin volver a hacer login), ya pudo acceder a /audit-logs.

  [x] BUG DE SEGURIDAD REAL encontrado y corregido durante las pruebas:
      un usuario desactivado (DELETE /users/{id}) SI podia volver a
      hacer login y obtener tokens nuevos, anulando la desactivacion.
      Se agrego la verificacion "is_active" en AuthService.login()
      (dominio: nueva excepcion AccountDeactivatedError). Verificado:
      ahora el login de una cuenta desactivada devuelve 403.

  [x] Verificacion funcional completa contra Postgres real (mismo patron
      de las fases anteriores, contenedor temporal ya eliminado): se
      registraron 2 usuarios, se promovio uno a admin (bootstrap manual
      via SQL la primera vez, ya que no existe un admin previo capaz de
      asignarlo por API), y se probaron los 4 endpoints con permisos
      correctos e incorrectos (403 cuando falta el permiso).

  [x] NOTA PARA FASE 8 (README, "mejoras futuras"): el primer usuario
      Admin del sistema hoy se crea manualmente en la base de datos
      (no hay un comando de "bootstrap" automatizado). Es una limitacion

[2026-07-27] FASE 5 - TESTING
--------------------------------------------------------------------

  [x] 20 tests UNITARIOS (tests/unit/): prueban AuthService y
      UserManagementService con repositorios FALSOS en memoria (no usan
      Docker ni Postgres, corren en ~4 segundos). Esto es lo que demuestra
      que el Repository Pattern de la Fase 1 no fue decorativo.

  [x] 10 tests de INTEGRACION (tests/integration/): prueban los endpoints
      reales de la API contra un Postgres real, usando el mismo patron de
      contenedor temporal que usamos manualmente en las Fases 2-4, ahora
      AUTOMATIZADO dentro de un fixture de pytest (arranca antes de la
      sesion de tests, corre las migraciones, y se autodestruye al final).
      No se agrego ninguna libreria nueva para esto (no testcontainers):
      se reutilizo subprocess + docker CLI, exactamente el mismo script
      que ya habiamos validado que funciona en este Mac.

  [x] PROBLEMAS TECNICOS ENCONTRADOS Y RESUELTOS (no eran bugs de la app,
      sino de como correr los tests):
        1. pytest-asyncio crea un event loop nuevo por cada test por
           defecto, pero el motor de base de datos de la app es un
           singleton a nivel de modulo (igual que en produccion, donde
           solo hay un event loop para toda la vida de la app). Esto
           causaba errores "attached to a different loop". Solucion:
           configurar pytest-asyncio para compartir un unico event loop
           en toda la sesion (asyncio_default_test_loop_scope = "session"
           en pyproject.toml).
        2. El rate limit de login (5/minuto) se disparaba entre tests
           porque todos comparten la misma "IP" simulada del cliente de
           pruebas. Solucion: se sube ese limite SOLO en el entorno de
           tests (variable de entorno RATE_LIMIT_LOGIN), sin tocar el
           limite real de produccion.

  [x] Se aprovecho para pasar "ruff" (el linter) sobre todo el codigo y
      corregir 90+ advertencias de estilo (lineas largas, una variable
      sin usar). Cero advertencias ahora: "ruff check src tests" -> OK.

  [x] Resultado final: 30/30 tests pasan (pytest -q). El contenedor de
      Postgres de test se crea y se destruye solo en cada corrida, no
      queda nada residual en Docker.

  [x] Se ejecuto "mypy" (modo strict) por primera vez desde que se
      configuro en la Fase 1 -- encontro 12 errores reales de tipado
      (no bugs de comportamiento, pero si huecos de tipado que un CI
      real habria bloqueado). Todos corregidos:
        - varios "dict" sin tipar -> "dict[str, object]" / "dict[str, Any]"
        - passlib no tiene stubs de tipos mantenidos -> se agrego un
          override en pyproject.toml para ignorar esa libreria puntual
        - hash_password/verify_password devolvian "Any" -> se envuelve
          el resultado en str()/bool() explicito
        - conflicto de tipos entre slowapi y Starlette en el handler de
          rate limit -> comentado y silenciado con type: ignore (es un
          desajuste conocido entre las dos librerias, no un bug real)
      Resultado: "mypy src" -> Success: no issues found in 51 source files

  [x] Creado .github/workflows/ci.yml con 4 jobs:
        lint              -> ruff + mypy
        unit-tests        -> pytest tests/unit (sin Docker)
        integration-tests -> pytest tests/integration (con Docker; los
                              runners de GitHub Actions ya traen Docker
                              instalado, así que el mismo conftest.py que
                              levanta Postgres localmente funciona igual
                              ahi, sin configuracion adicional)
        docker-build      -> construye la imagen de produccion, solo si
                              los 3 jobs anteriores pasaron
      Los 3 primeros corren en PARALELO (mas rapido); docker-build espera
